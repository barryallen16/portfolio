Partha Tamil Tokenizer

Agglutinative BPE tokenizer engine written in Rust

→ -50.2% tokens vs OpenAI o200k · +36.9% vs mBERT

Playground Source Weights
Partha Engine Core
Rust · Rayon · CSR Index
Base Vocab: 1,135 stems
Fidelity: 100% decode
Compression: -50.2% vs o200k · 0.9193 bits/byte

[problem] General subword tokenizers (mBERT, Llama-3) fragment agglutinative Tamil into arbitrary byte shards, tripling sequence length, blowing KV-cache budgets, and corrupting 52% of Latin-1 decodes.

[tradeoff] Writing a custom BPE training engine in Rust gained raw training speed, but required engineering merge tracking, CSR matrix indexing, and Hugging Face export tooling from scratch.

[solution] Constructed a 1,135-token base vocabulary around Tamil conjunct stems, Aho-Corasick parallel merges with Rayon, and CSR indexing. Yields 50.2% fewer tokens than OpenAI o200k, achieving 0.9193 bits/byte on Tamil wiki (+36.9% vs mBERT) with 100% decode fidelity.

  • • 50.2% fewer tokens vs OpenAI o200k with +16.5 accuracy gain on Tamil classification
  • • Custom BPE merge table built specifically for Tamil morpho-phonemics
  • • Aho-Corasick multi-pattern merge tracking with Rayon data parallelism
  • • CSR (Compressed Sparse Row) matrix indexing for memory-bounded vocabulary compaction
Rust Rayon Aho-Corasick BPE HuggingFace

FitCheck

Local VLM outfit recommendation and weather intelligence

→ IEEE TQCEBT 2026 · 3.1x VRAM reduction

Showcase Paper Source Models
IEEE Peer-Reviewed System
DOI: 10.1109/TQCEBT67648.2026.11681836
Study: 297 human ratings
Significance: r=0.303, p<0.05
Distillation: 8B teacher → 2B student (28K LoRA steps)

[problem] Multimodal outfit recommendation models require heavy cloud GPUs, but uploading personal wardrobe photos violates user privacy and fails without internet access.

[why ai] Aesthetic harmony, color theory, seasonal weather compatibility, and cultural styling cannot be encoded in rigid if/else trees; they require vision-language embeddings to score visual cohesion.

[tradeoff] Distilling an 8B vision-language teacher into an on-device 2B student saved 3.1x VRAM, but required 28K LoRA steps across 538K caption-QA pairs to preserve 92% scoring quality.

[solution] Offline-first React Native Android app with local SQLite, Open-Meteo weather scoring, and on-device GGUF inference via LM Studio. Validated in a blind human study (297 ratings, r=0.303, p<0.05) and published in IEEE TQCEBT 2026.

  • • Teacher-student LoRA distillation (8B VLM to 2B student) saving 3.1x VRAM
  • • Offline SQLite schema with weather-adaptive scoring heuristics
  • • Validated in a peer-reviewed blind human study published in IEEE

D1-Triage

Sub-15ms Java vulnerability triage using Liquid AI Hybrid SSM

→ 12ms inference · 0.8372 AUC on verified fixes

Demo Source Weights Dataset
Liquid AI SSM Classifier
d1-3B · 6.25 GiB VRAM on T4
Latency: 12-14 ms
Fix AUC: 0.8372 vs 0.7167 Kev-4B
Benchmark: 174 Java CVEs · 416 verified diffs

[problem] Static analysis scanners like Semgrep emit hundreds of unranked alerts per repository, with false-positive rates exceeding 70% and burying real vulnerabilities under low-priority warnings.

[why ai] Static AST rules lack execution reachability context. Determining whether tainted user input reaches an exploitable sink requires reasoning over method logic, sanitizers, and control flow.

[tradeoff] Fine-tuning on synthetic benchmarks caused distribution collapse, dropping within-rule AUC to 0.449. Training on 416 real pre/post-fix diffs prevented collapse, but required statement-level sink anchoring to align unnumbered method snippets with reported scanner line numbers.

[solution] Fine-tuned Liquid AI d1-3B hybrid SSM to classify alert exploitability in 12-14 ms on an Nvidia T4 using 6.25 GiB VRAM. Achieved 0.8372 AUC on verified fix hunks (exceeding Kev-4B's 0.7167) and 0.6594 within-rule AUC across 174 real-world Java advisories.

  • • Statement-level sink anchoring across 416 real diffs preventing collapse
  • • 12-14 ms latency on single T4 GPU with 6.25 GiB VRAM footprint
  • • Outperformed Kev-4B by +0.1205 AUC on exploitability classification

Sivabharani Comments

High-throughput Tamil tech video transcript search pipeline

→ 1.18M chunks indexed across 1,400+ videos

Search Source Dataset
Distributed Extraction Pipeline
27 Groq Keys · Meilisearch
Corpus: 1,400+ videos
Search: <50ms response
Precision: Micro-chunk second-accurate pinning

[problem] Locating specific community discussions across 1,400+ Tamil tech videos (1.18M transcript chunks) required scrubbing through hundreds of hours of raw audio.

[why ai] YouTube transcripts feature Tanglish (Tamil spoken in English script), conversational digressions, and colloquial name mentions that standard regex and named-entity recognizers fail to parse.

[tradeoff] Relying on free-tier Groq API instances kept compute costs at zero, but demanded a custom 27-key worker pool with dynamic rate-limit header parsing across 1.18M chunks.

[solution] Distributed extraction pipeline with 65-second overlapping conversational windows. Micro-chunk timestamp pinning maps extracted commenter names to exact video seconds, indexed in Meilisearch.

  • • 27-key worker pool with dynamic 429 rate-limit backoff handling
  • • Overlapping 65-second sliding windows for contextual entity retention
  • • Micro-chunk timestamp pinning mapping commenters to exact video seconds
